Difficulty You Can Prove

Updated 20 Oct 2026 · Code verified against Zig 0.18.0-dev.753+1420479be

The course generator puts down rows of blocks. The rows must become more difficult, and they must stay possible.

A mistake here does not look like a bug. Each row still has an open lane and the game still runs, but nobody can survive the course. The only sign is that people stop their play.

The spacing has a minimum

Between the arrival of one row and the next row, the player can have to cross the full board. That costs two lane changes. Also, the player cannot start while the current row is level with the player. A move to the side into a block next to you is a crash.

The smallest spacing that a player can still survive is the sum of these two times.

The second term becomes smaller when the game becomes faster, because a faster row is next to you for less time. The first term does not change with the speed.

Calculate the spacing, do not adjust it by hand

The first version had two constants that a person selected: an easy spacing and a hard spacing. The game interpolated between them. This method worked. But it had three numbers that had to agree, and nothing in the code said so. If you changed the lane change time, the hard spacing became impossible without an error.

Now the code calculates the spacing from the minimum, and the spacing decays toward the minimum.

The decay never gets to the minimum, and this fixes a second problem. The earlier curve got to its most difficult setting at sixty seconds and then stayed there. A sufficiently good player never lost.

One named constant now holds the margin above the impossible spacing.

Prove it with play

All of this is still an argument about four constants. That type of argument is easy to get wrong. Thus a program plays the game.

The policy looks at the next two rows. It does three things:

  • It selects a lane that is open in the first row.
  • It does not start a move across the board that it cannot complete in time.
  • It does not take a path that slides through a block that is level with it now.

Then a test runs the bot for four minutes of game time at each seed.

The test failed on its first run, at seed 21, after 8.2 seconds of play.

What the test found

The bot steered into blocks that it thought were behind it. It ignored each block whose centre was behind the centre of the player. It measured this distance with only the half height of the block. The correct number is the sum of the two half heights. Each body is 52 units tall. Thus a block whose centre is 41 units behind you still overlaps you.

The title of the regression test states the case:

Each unit test passed while this bug existed. The collision code was correct by itself. The generator and the spacing were also correct. The error was in the logic that connected these parts. Only a full run of the game tests that logic.

Solvable and playable are different

A bot with no reaction time can survive a course. That result proves that the course is solvable. It does not tell you if a person can play the course.

Thus the same policy runs again with a delay before it.

The model contains only latency. The bot acts now on the decision that it made from the world as the world was some ticks ago. An earlier version counted down a timer and reset the timer each time that the ideal lane changed. When the policy could not choose between two lanes, that version livelocked. The model reported that the game was much more difficult than it really was. Some time passed before anybody saw that the fault was in the model and not in the game.

The numbers from the model are the difficulty curve:

ReactionMean run
100 ms58 s
150 ms46 s
200 ms30 s
250 ms26 s
300 ms24 s

Thus a slow, calm player gets half a minute, and a fast player gets a minute. All players lose at some time. That part took the most work.

The test asserts the shape and not the values. Thus you can adjust the numbers and not rewrite the test.

The last assertion found the flat difficulty curve. A fast player had an average of the full limit of three hundred seconds, and every other test passed.

Two smaller rules

The start is easy. During a grace window, no row blocks more than one lane. In the first few seconds, one small move is sufficient for each row.

This rule is a decision, not a measurement. The reaction time model already knows the controls perfectly. Thus the model cannot show the problems of a player who still looks for the keys. When the window is off, the modelled 200 ms average moves by three tenths of a second.

Coins show the safe lane. The spawner puts a coin only in a lane that its own row leaves open. When a row blocks two of the three lanes, the coin is in the one gap. A player who follows the coins follows the safe path, and nobody has to tell the player. The rule is four statements in the spawner. The game has no other tutorial.
