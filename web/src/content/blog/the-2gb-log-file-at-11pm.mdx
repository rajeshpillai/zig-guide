## 10:52 PM

Shivam's phone buzzed on the kitchen table. The alert was the one that nobody wants: **Checkout error rate above 5%.**

Shivam was on call this week. When production breaks at night, the person on call repairs the problem. This week, that person was Shivam.

Shivam opened the laptop. A message from Urvashi in support was already there.

> Customers say payment hangs and then fails. Started maybe 20 minutes ago?

"Maybe" was not sufficient. Shivam had to know which part of the site was slow, and when the problem started.

## 10:58 PM

Shivam logged in to the web server, `web-03`, and examined the access log.

```sh
$ ls -lh /var/log/shop/access.log
-rw-r----- 1 shop shop 2.0G Oct  3 22:58 /var/log/shop/access.log
```

The log was two gigabytes: fifty million lines, with one line for each request. Each line had this shape:

```txt
2026-10-03T22:41:07Z POST /api/checkout 504 5000
```

The fields are the time, the method, the path, the status code, and the duration of the request in milliseconds.

Shivam knew what the report had to show:

- The number of requests for each status code.
- The endpoint that was slow.
- The time of the first `504`. A `504` means that the request timed out.

The server had `awk`. The server did not have Python. And this week, the rules let nobody install software on production servers.

Shivam could write the report in `awk`. But an average for each endpoint, a maximum and "the first 504" make a long `awk` line.

Shivam wanted a program to test on the laptop first. Then Shivam could trust the program on the server. Thus Shivam opened a new file: `logscan.zig`.

## 11:04 PM: one line at a time

Shivam wrote the smallest part first: a function that splits one line of text into fields.

<SnippetSource name="blog.logscan" decl="parseLine" />

The function returns `?Line`. The `?` means "a `Line`, or `null`".

Shivam knew that the log had bad lines. When a customer closes the tab in the middle of a request, the server writes `-` in place of the milliseconds.

`parseInt` fails on `-`. Thus `parseLine` returns `null`, and the caller counts the line as skipped. The caller adds one to `skipped` and continues to the next line.

## 11:10 PM: read 2 GB with 64 KiB

The server had less than 1 GB of free memory. Thus Shivam could not read the full file into memory first.

Shivam gave the reader a buffer of 64 KiB:

```zig
var buf: [64 * 1024]u8 = undefined;
var reader = file.reader(io, &buf);
```

The reader fills the buffer from the file. `takeDelimiter('\n')` returns the next line as a slice of that buffer. When the program uses all of the bytes in the buffer, the reader fills the buffer again.

The file can be of any size. The memory for the read operation stays at 64 KiB.

<SnippetSource name="blog.logscan" decl="scan" />

The code has one more case. If a line is longer than the full buffer, the reader gives `error.StreamTooLong`. The loop skips that line and continues.

## 11:17 PM: the bug that almost happened

For each endpoint, Shivam kept a total in a hash map. The first version stored `line.path` as the key.

Then Shivam stopped. `line.path` is a slice of the reader's buffer. When the reader fills the buffer again, the reader writes new bytes over those bytes.

If the map keeps those slices, each key in the map changes to different text. Nothing reports an error.

Thus the program copies each key when the key occurs for the first time:

<SnippetSource name="blog.logscan" decl="add" />

In many languages, when you read a line, you get a new string that you own. In Zig, the line is a view into the reader's buffer.

For this reason, a read of a line allocates no memory. For the same reason, you must copy a line that you want to keep.

## 11:24 PM: test it on the laptop

The real log was not on the laptop. Thus Shivam gave the program a second mode.

If you give the program no file name, the program writes a sample log of 50,000 lines. Then the program scans that log.

The sample is one hour of invented traffic. From 22:40, the checkout endpoint becomes slow, and some requests time out. The real endpoint did the same.

Press **Run** to see the report.

<Playground name="blog.logscan" />

The program ran in your browser. The program wrote a 2 MB file. Then the program read the file again through the 64 KiB buffer.

Look at the checkout row. The average is 699 ms. The number is bad, but not very bad, because the average includes forty normal minutes and twenty slow minutes.

The last line gives the useful fact: the first `504` was at 22:40:00.

## 11:31 PM: one file, no install

Now the program had to run on `web-03`. The server runs Linux on x86-64. Shivam's laptop could build a program for that server directly:

```sh
$ zig build-exe -O ReleaseFast -fstrip -target x86_64-linux-musl logscan.zig
$ ls -l logscan
-rwxr-xr-x 1 shivam shivam 273624 Oct  3 23:31 logscan
$ file logscan
logscan: ELF 64-bit LSB executable, x86-64, version 1 (SYSV), statically linked, stripped
```

`-target` gives the machine for the build: x86-64, Linux.

This program does not use a C library at all. The Zig standard library makes calls to the Linux kernel directly.

Thus the result is "statically linked": the file needs nothing else on the server. The server does not need a runtime, shared libraries or a package.

The file was 274 KB. Shivam copied the file to the server.

```sh
$ scp logscan web-03:/tmp/
```

## 11:33 PM: the real file

```sh
$ /usr/bin/time -f "%e s, %M KB" /tmp/logscan /var/log/shop/access.log
read 50000000 lines, 2075125000 bytes, through a 65536-byte buffer
skipped 51000 lines we could not parse

status  requests
  200  48471000
  404    934000
  504    544000

endpoint         requests  avg ms  max ms
  /api/checkout   9996000     699    5000
  /api/search     9970000      89     119
  /api/cart       9912000      59      79
  /login         10115000      37      49
  /               9956000      17      23

first 504 at 2026-10-03T22:40:00Z
6.45 s, 652 KB
```

The program read fifty million lines in about seven seconds. The full process used 652 KB of memory.

Shivam also ran `awk` on the same file, to compare. The `awk` command counted only the status codes, and it took about 13 seconds.

## 11:36 PM

Shivam put the report in the incident channel.

> Only checkout is slow. Everything else is normal. First timeout at 22:40:00. What shipped around 22:40?

Two minutes later, Urvashi replied.

> Payments team changed the timeout config for the card provider at 22:39.

The payments team reverted the change at 11:41 PM. At 11:52 PM, the checkout error rate was zero again.

## The next morning

Shivam added `logscan.zig` to the tools repository of the team. The program is about 220 lines.

Each person on the team can build the program for any server with one command. This also works for the ARM machines:

```sh
$ zig build-exe -O ReleaseFast -fstrip -target aarch64-linux-musl logscan.zig
```

## Try it yourself

The full program is above the Run button.

1. Press **Copy**.
2. Save the program as `logscan.zig`.
3. If you do not have Zig, [install Zig](/learn/getting-started/installation/).
4. Run one of these commands:

```sh
$ zig run logscan.zig                     # writes access.log and scans it
$ zig run logscan.zig -- /path/to/your.log
```

Your own log will have a different format. Change `parseLine` for that format. The other code stays the same.

These chapters give more detail about each part:

- [Read line by line](/learn/files/read-lines/). This chapter also shows lines that are longer than the buffer.
- [Hash maps](/learn/standard-library/hash-maps/). This chapter also shows who owns the keys.
- [Cross-compilation](/learn/build-system/cross-compilation/). This chapter shows how to build for a different machine.

## About the numbers

Shivam, Urvashi and `web-03` are not real. The numbers are real.

The 2 GB file is 1,000 copies of the sample log. Each time and size in this post is a measurement from a laptop with an Intel Core i5-1235U. The measurements used the Zig version at the top of this post.

In three runs, `logscan` took between 6.4 and 8.2 seconds. The memory of `logscan` stayed at 652 KB in each run. The output above is from the fastest run.

The `awk` command was `awk '{c[$4]++} END{for(k in c) print k, c[k]}'`. This command counts status codes and does nothing else.
