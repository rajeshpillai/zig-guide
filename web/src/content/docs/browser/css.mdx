A stylesheet is a list of rules, and a rule is a selector plus some
declarations. Parsing it is simple: split on `{`, split on `;`, split on `:`.

The hard part is that **several rules match the same element and say
different things**, and something has to decide which one wins. That decision
is the cascade, the C in CSS.

## The rule

Two comparisons, in order.

1. **Specificity.** How precisely does the selector describe the element?
2. **Source order.** If specificity ties, the later rule wins.

Those two comparisons are the whole cascade. When CSS seems unpredictable,
the cause is usually a wrong idea of how specificity works.

## What just happened

**`<p class="warning" id="urgent">` got `color: crimson`.** Every rule in the
sheet matched it, and four of them set a colour: black, orange, red and
crimson. `#urgent` won because an id beats any number of classes, and that is
specificity.

**The same element got `margin: 8`, from `p.warning`.** Three rules set
margin, and two of them are the plain `p` at specificity 0,0,1. `p.warning` at
0,1,1 beats both. The class component decides it.

**The plain `<p>` got `margin: 4`, from the last rule.** Two rules with the
identical selector `p` both set margin. Specificity ties, so source order
decides, and the later one wins. This is why people tell you to "put your
overrides at the bottom".

**Specificity is three numbers, not one.** The output shows them separately:
`0,1,1` for `p.warning`, `1,0,0` for `#urgent`. They are compared left to
right, like version numbers, so any id beats any number of classes.

## Check yourself

You will often see specificity described as a single score: 100 for an id, 10
for a class, 1 for a tag, add them up. Where does that break?

At eleven classes. It scores 110 under that scheme, which beats an id's 100.
In a real browser it does not. The comparison is component by component, so an
id beats any number of classes no matter how large the middle number gets.

The single score is a teaching shortcut. It gives the right answer for every
realistic stylesheet, so people keep using it. But when you build something
that *computes* specificity, one number is a bug. The implementation above
uses a struct with three fields for that reason.

## What this one leaves out

**Inheritance.** Some properties, `color` among them, are inherited by children
that do not set them. Others, `margin` among them, are not. The spec defines
this for each property. The next chapter needs it, because a paragraph inside
a styled div has to get its colour from somewhere.

**Combinators.** `div p` matches a `p` with a `div` ancestor, and `div > p`
requires it to be the parent. Both need the tree, not just the node, so
matching becomes a walk upwards through the ancestors. For this reason, real
engines match selectors right-to-left. They start from the element they have
and walk up. They do not find every candidate and search down.

`!important` sits above specificity entirely. The reason it exists at all is
user stylesheets: a reader who needs larger text has to be able to overrule
the page.

## If you have written C

The parsing is `strtok` on braces and semicolons, with no surprises. The
matching needs more thought, because it is the hot loop of a browser.

The simple approach tests every rule against every element. That costs rules
times nodes, which is far too slow for a real stylesheet on a real page.
Engines instead index the rules by their rightmost component, in hash maps
keyed on tag, class and id. An element then tests only the few rules that
could match it. This index is why the shape of your selectors affects
performance at all. It is also why a selector ending in `*` is the slow one.

The other C-specific concern is that every string here points into the
stylesheet source, so the source must outlive the parsed rules. The rest of
this track makes the same borrowing decision. In a browser, this is why a
stylesheet's bytes stay alive for as long as the page does.
