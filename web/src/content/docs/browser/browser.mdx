Each stage has had a chapter. This one runs them in a row. The pipeline is the
answer to "how does a browser work", and here you can see it in forty lines of
code.

```
bytes ─► tree ─► boxes with widths ─► boxes with positions ─► pixels
        (HTML)      (CSS + layout)         (layout)            (paint)
```

There are five stages, and each one takes only what the previous one produced.
This separation is what makes a browser possible to build at all. The HTML
parser knows nothing about pixels. The painter knows nothing about tags.

## What just happened

**One declaration changed and the page rearranged itself.** `h1 { height: 30 }`
became `height: 60`, and everything below moved down. Nothing else in the
stylesheet or the document was touched.

This is the reason stylesheets exist. The height of the box is an input to
layout. Every position below it is computed, not stored. Change the input, run
the two passes again, and you get a new set of positions. Nothing was written
down twice, so there is nothing to keep in sync.

**The counts are printed for each render.** 11 nodes, 4 rules, 11 boxes. The box tree and the node tree happen to be the same size here. In general
they are not: some elements produce no box, and a single element can produce
several, one per line of text or one per table cell.

**Each stage is replaceable.** The renderer writes characters; swapping it for
one that writes RGBA changes nothing upstream. The layout engine does block
flow; adding flexbox means a different function producing the same `Box`
values. Because the stages are separate, browsers can rewrite one stage at a
time.

## What a real browser adds, in order of how much

**Everything is incremental.** Nothing above caches anything: a second render
redoes all five stages. A real engine tracks which nodes have changed, which
boxes need layout again, and which regions need repainting. A page can have
fifty thousand nodes, and a blinking cursor must not re-render all of them.
The code that tracks these changes is larger than the pipeline itself.

**Everything is concurrent.** Parsing happens while bytes are still arriving.
Images decode on other threads. Painting happens on a compositor thread so
scrolling stays smooth while JavaScript is busy. The pipeline keeps the same
shape. Several copies of it just run at once.

The versions here show the shape of each stage with the details removed. The
details are what take years to build: the HTML parser's 80 tokenizer states,
CSS's dozen layout modes, text shaping, bidirectional text, and thirty years
of old pages that must keep working.

## Check yourself

The pipeline is drawn as one direction, but a script can change the document.
What does that do to the diagram?

A script changes the tree. The old boxes are then out of date, so layout and
paint must run again. The browser tries to do this once per frame, not once
per change.

A script that reads a size like `offsetHeight` in a loop that also writes
forces a full layout on every iteration. This is called *layout thrashing*,
and [the layout chapter](/learn/browser/layout/) explains it.

## Where this section ends

Six chapters. A parser that cannot fail. A cascade that decides between rules.
Two passes that turn a tree into rectangles. A painter that fills them. And a
scripting engine attached at one point. Together they have the shape of a
browser. Everything that makes a real browser hard to build has been left out.

If you liked the graphics part, [the graphics section](/learn/graphics/)
does rasterisation properly, with real pixel buffers, line and triangle
drawing, antialiasing and image files. If you liked the language part, [the
Tiny Language section](/learn/tiny-lang/lexer/) builds the scripting engine
that this section only sketched.
