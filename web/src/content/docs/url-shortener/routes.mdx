All five CRUD routes of a URL shortener fit in one Zig function. `handle`
takes request bytes and a store, and writes a complete HTTP response. An
in-memory store is behind the seam. Thus the tests of each route need no
server, no socket and no database.

## The problem

In the HTTP surface, create, read, update and delete become routes. This layer
also has the most cases that you must make correct:

- The slug that does not exist.
- The URL that fails validation.
- The method that no code handles.

If you test those cases against a live server and database, you must start
the server and the database for each case.

The solution is the same seam that the [ORM's Repo chapter](/learn/orm/repo/)
built. Put the storage behind an interface. Then give the handler the
implementation that it needs at that time. The in-memory store needs no server
and no database. Thus this chapter runs in your browser.

## The plan

1. A `Store` that holds links in a fixed array. The store has only the methods
   that the routes can use: create and find.
2. `handle`: parse the request line, dispatch on the method and the path, and
   write a complete HTTP response. The request parsing is the minimum that
   works. The [web server track](/learn/web-server/request/) shows the full
   parsing.
3. A demo that runs all five routes and the failure cases, and prints each
   exchange.

## Read the trace as a contract

The demo is the specification of the service, with one exchange for each case:

- Create answers 201 with the slug.
- The bad scheme answers 400, before the storage gets the request.
- The redirect answers 302 and counts the hit.
- Update changes the target of the same slug.
- Delete answers 204.
- A slug that does not exist now answers 404.

The final chapter replaces the store with SQL. After that change, this trace
must stay true.

## The order of the routes is important

The handler matches `/links` and `/links/{slug}` before the general slug route.
Thus a link with the slug `links` is not reachable. The alphabet from the slugs
chapter makes that collision impossible now: `links` decodes to a very large
id, not to an early id.

But route shadowing occurs with no warning. Suppose a person adds `/stats` to a
slug space that grows. No part of the system gives a warning. Keep all reserved
paths under one prefix, as `/links/...` does. This is an easy way to prevent the
problem.

## Variations

- **No allocation:** the store is a fixed array, and the handler builds each
  response in a buffer that the caller owns. A service of this size can decide
  its limits at the start. When the array is full, the service answers 507.
- **Add a route:** a `GET /links` listing is one more branch and one more store
  method. The handler cannot go around the seam. It must ask the store for all
  the data that it needs.
