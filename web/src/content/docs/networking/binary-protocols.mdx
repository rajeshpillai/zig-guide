Each binary protocol starts with a fixed-size header. Thus the receiver can
read a known number of bytes before it knows other information. To write a
header, you must obey two rules. The rules are easy to state, and they are
also easy to forget.

<Playground name="11-networking.binary-protocols" />

## A struct is not a wire format

```
@sizeOf(Header) = 12, on the wire = 10
```

The struct is larger than the message. Zig can pad a struct, and Zig can
change the order of its fields. You do not control the padding bytes. They
contain the data that was in that memory before. If you send the struct, you
send two bytes of other data. Also, the layout that you send is the layout
that your compiler selected for your target today.

```zig
// Do not do this.
try socket.writeAll(std.mem.asBytes(&header));
```

`extern struct` makes the layout fixed. It is the correct tool for calls to
C, as [ABI](/learn/working-with-c/abi/) shows. But `extern struct` does not
make the byte order fixed, thus it is not sufficient here.

Write the fields:

```zig
try w.writeInt(u16, self.magic, .big);
try w.writeInt(u8, self.version, .big);
```

This method needs more code. It is also the only method that still works
with a different compiler, a different target, or a peer in a different
language.

## Say which end first

```
length read as big-endian:    5
length read as little-endian: 83886080
```

No function returned an error. The length is only wrong, but it is wrong in
a dangerous way. If a receiver trusts this length, the receiver tries to wait
for 83 megabytes, or to allocate 83 megabytes. The cause is one message of
five bytes.

By convention, network byte order is big-endian. Obey the convention, also
when the two ends are little-endian computers today. One day, one of the two
ends will possibly not be little-endian. State the endianness at each call.
`readInt` and `writeInt` require the argument, thus you cannot forget it.

The [Byte Order](/learn/language-basics/integer-rules/) rules are most
important here. Inside your process, byte order is never a problem.

## Reject before you trust

```
an HTTP request into this parser: NotOurProtocol
```

The parser checks the magic number before it reads a length. When a port on
the internet opens, it receives HTTP requests, TLS handshakes and scanner
probes in a few minutes. If you let the parser accept them, each of these
messages will parse as *something*. Two bytes of magic make the parser
reject them immediately.

The same rule applies to the tag byte:

```zig
.kind = std.enums.fromInt(Kind, kind) orelse return error.UnknownKind,
```

An attacker can control a byte from the wire. If you use `@enumFromInt` on a
value that is not a valid tag, the behaviour is undefined.
`std.enums.fromInt` returns null for that value. `std.enums.fromInt` replaced
`std.meta.intToEnum`, which does not exist now. If your code uses
`std.meta.intToEnum`, change it to `std.enums.fromInt`.
