The previous chapter showed that a stream has no message boundaries. Framing
adds the boundaries again. There are three ways to frame a message. Each
protocol that you know selects one of these three ways. The hex below shows
each of the three.

<Playground name="11-networking.framing" />

## Length prefix

```
00 04 50 49 4e 47
^^^^^ length      ^^^^^^^^^^^ payload
```

Before the receiver reads one byte of payload, the receiver knows exactly how
many bytes to wait for. This property makes the parser in the last chapter
possible. For this reason, a length prefix is the default selection for all
binary data.

The framing does not change the payload. Thus the payload can contain any
byte, and also the newline that the next method cannot carry. The cost is
that you must know the length before you start to write. Thus you must put
the full message in a buffer, or know its size before you start.

## Delimiter

```
50 49 4e 47 0a
^^^^^^^^^^^ payload  ^^ '\n'
```

A delimiter is cheap to write and cheap to read. A person can also read it
on the wire. For these reasons, HTTP, SMTP, IMAP and Redis use a delimiter
for their text parts. You can debug the protocol with `nc`, because you can
read the bytes.

The cost is that the delimiter byte can never occur in a payload. The last
line of the output shows what occurs when the payload contains the byte. The
reader stops too early and does not report an error. For the reader, the
message ended at the correct place for the end of a message. The reader uses
the other bytes as the next message.

Real protocols solve this problem in one of two ways:

- They escape the delimiter byte in the payload.
- They put a length prefix on the body only.

HTTP uses the second way: headers with delimiters, then `Content-Length` and
a raw body.

## Self-describing

```
69 00 00 10 00   73 00 04 50 49 4e 47
^^ 'i'           ^^ 's'
```

A tag byte tells the receiver how to read the bytes after the tag. Here, `i`
means a fixed-width integer and `s` means a length-prefixed string. Thus the
receiver does not need an agreement before the message about the contents of
the field.

RESP, protobuf wire types, MessagePack and CBOR use this shape. The cost is
one byte for each value. You also need a `switch` that rejects unknown tags.
The `switch` must not trust an unknown tag.

## Select a method

The other two methods are special cases of a length prefix. A delimiter is a
length that you must search for. A tag is a length that also carries its
meaning. If you design a new protocol, and it is not necessary for a person
to read it, use a length prefix.

If you want to debug the protocol by hand, use a delimiter for the envelope
and a length for the body. HTTP used that combination for thirty years.
