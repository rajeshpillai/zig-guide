A Zig program can use the PostgreSQL wire protocol with no driver. After the startup message, each message has three parts: a one-byte type, a big-endian `Int32` length that counts itself, and the payload.

## The problem

A Postgres driver is mostly a codec for one TCP protocol. When you see that protocol without a driver, you see the real cost of a query, and the cause of a hang.

This recipe implements a part of both ends, sufficient to complete a startup handshake and run one query. Thus the exact bytes are on the page.

The other database recipes run a mock backend in the same process, and this recipe does too. Thus CI runs the full exchange and compares the output, without a `postgres` that runs. The framing is the real protocol. Only the authentication and the query engine are stubs.

## The plan

1. All of the integers are big-endian. Write one `putInt` and one `getInt`, and use them everywhere.
2. Send a `StartupMessage`. It has no type byte, only a length and a list of parameters that ends in a null.
3. Read the reply stream of the backend until `ReadyForQuery` (`Z`). Decode each message by its type byte.
4. Send a `Query` (`Q`). Then read `RowDescription` (`T`), `DataRow` (`D`), `CommandComplete` (`C`) and the next `ReadyForQuery`.

## Two message shapes

After the first message, each Postgres message has the same frame:

1. a one-byte type
2. an `Int32` length that counts itself but not the type byte
3. `length - 4` bytes of payload

`sendMsg` and `readMsg` encode exactly that frame. Thus the other code works only with payloads.

The startup message is the one exception. It is older than the type-byte convention. Thus it is only a length and a body. Because of this difference, `sendStartup` and `readMsg` are separate.

## The handshake is a stream, not a call

When you send the startup message, you do not get one reply. The backend replies with a sequence of messages:

1. `AuthenticationOk`.
2. One `ParameterStatus` for each server setting (`server_version`, `client_encoding`, and usually about twelve more).
3. `BackendKeyData`, with the process id and the secret that a client uses to cancel queries.
4. `ReadyForQuery`.

The client loops until it sees `Z`. That message tells the client that the connection is ready to use. A real driver caches the parameters and the cancel key here.

## Read a result

A query replies with the same stream shape:

- `RowDescription` gives the names of the columns and their types.
- `DataRow` contains one row as column values, each with its length before it. A length of -1 means SQL `NULL`.
- `CommandComplete` reports the tag.
- `ReadyForQuery` closes the batch.

The `Cursor` helper moves through a payload with an index. It reads integers and null-terminated strings. These messages need only that parse.

## Flush, or the program hangs

Each send here has a flush after it, because the first version of this recipe hung without the flush. The socket writer has a buffer. Thus a message that you "sent" stays in your buffer until you flush.

If both sides then block on a read, neither side can continue. This is a common deadlock in wire protocols. It is easy to cause this deadlock when a flush does not immediately follow a send.

## Variations

- **Real authentication:** the backend can reply to the startup with `AuthenticationCleartextPassword` or with an MD5 or SCRAM challenge, in place of `AuthenticationOk`. The client replies with a `PasswordMessage`, and the loop continues.
- **Prepared statements:** the extended-query protocol replaces `Q` with `Parse`, `Bind` and `Execute`. With this protocol, parameters stay out of the SQL text.
- **A local database:** to keep data without a server or a protocol, [SQLite from Zig](/learn/how-to/databases/sqlite-basic/) links the C library directly.
