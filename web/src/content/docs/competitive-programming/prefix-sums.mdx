Suppose we have an array and need to answer many range-sum queries.

For one query, we can simply loop over the required values and add them.

That is fine when there are only a few queries.

But if we have 100,000 values and 100,000 queries, repeatedly scanning each range can require billions of additions.

A prefix sum prepares the array once.

After that, the sum of any range can be found with one subtraction.

## Building the prefix array

<SnippetSource name="23-competitive.prefix-sums" decl="buildPrefix" />

The prefix array stores cumulative sums.

We define:

`pre[i]`

as the sum of the first `i` values.

Because of this definition, the prefix array has one more cell than the original array.

`pre[0]` is the sum of zero values, so it is 0.

`pre[1]` contains the first value.

`pre[2]` contains the sum of the first two values.

And so on.

For example:

```
  idx    0   1   2   3   4   5   6   7
  val    3   1   4   1   5   9   2   6

the prefix array holds 9 cells for 8 values
  idx    0   1   2   3   4   5   6   7   8
  pre    0   3   4   8   9  14  23  25  31
```

The prefix indices are easier to understand as boundaries.

`pre[3]` is 8 because the three values before index 3 are:

`3 + 1 + 4`

`pre[0]` represents the boundary before the first value.

`pre[8]` represents the boundary after the last value.

The extra cell at index 0 is useful.

Without it, a range starting at index 0 would need a special case.

For example, code based on `pre[lo - 1]` would fail when `lo` is 0.

By storing the extra zero at the beginning, the same formula works for every range.

## Range sum with one subtraction

<SnippetSource name="23-competitive.prefix-sums" decl="rangeSum" />

Suppose we want the sum of the half-open range:

`[lo, hi)`

`pre[hi]` contains the sum of everything before `hi`.

`pre[lo]` contains the sum of everything before `lo`.

So the range sum is:

`pre[hi] - pre[lo]`

Everything before `lo` appears in both values and cancels out.

For example:

```
  range   pre[hi] pre[lo]   sum  values
  [0,3)         8       0     8  [ 3   1   4]  1   5   9   2   6
  [2,5)        14       4    10    3   1 [ 4   1   5]  9   2   6
  [1,8)        31       3    28    3 [ 1   4   1   5   9   2   6]
  [4,4)         9       9     0    3   1   4   1   5   9   2   6
  [0,8)        31       0    31  [ 3   1   4   1   5   9   2   6]
```

The important point is that the cost does not depend on the width of the range.

The range `[0,3)` has three values.

The range `[1,8)` has seven values.

Both queries use the same two prefix-array reads and one subtraction.

The empty range `[4,4)` also works naturally:

`pre[4] - pre[4] = 0`

No special case is required.

The full array is:

`pre[8] - pre[0]`

which gives 31.

Using half-open ranges also matches normal Zig slicing.

If an inclusive range is used instead, the formula becomes:

`pre[hi + 1] - pre[lo]`

The idea is the same.

## When prefix sums are useful

<SnippetSource name="23-competitive.prefix-sums" decl="rangeSumByLoop" />

Building the prefix array takes O(n).

Each range query after that takes O(1).

So prefix sums are useful when the array stays unchanged and we need to answer many queries.

For this small example:

```
  build once, then 5 lookups     8 adds
  rebuild before each lookup    40 adds
  no prefix array at all        21 adds
```

Building the prefix array once requires eight additions.

After that, all five queries use subtraction only.

For an array this small, directly adding the ranges requires only 21 additions.

So the difference is not large.

The benefit becomes important when there are many values and many queries.

There is also an important limitation.

If the original array changes, the prefix array becomes outdated.

Suppose we change the value at index 3.

Every prefix value after that position may now be wrong.

Rebuilding the prefix array costs O(n).

So prefix sums are not a good choice when updates and queries are mixed frequently.

For that kind of problem, data structures such as a Fenwick tree or segment tree can handle both updates and queries in O(log n).

Prefix sums and sliding windows solve different problems.

A prefix sum can answer arbitrary range queries in any order.

A sliding window is usually useful when ranges are processed in sequence and one range is closely related to the next.

[Sliding Window](/learn/competitive-programming/sliding-window/) covers that pattern.

## Difference arrays

<SnippetSource name="23-competitive.prefix-sums" decl="applyRange" />

Now consider the opposite type of problem.

Instead of many range queries, suppose we have many range updates.

For example:

- add 5 to every value in `[0,3)`
- subtract 1 from every value in `[2,6)`
- add 10 to every value in `[4,8)`

The direct approach updates every value inside every range.

That costs O(width) for each update.

A difference array lets us record each range update with only two writes.

Instead of changing every value immediately, we record where the change starts and where it stops.

For example:

```
  update          0   1   2   3   4   5   6   7   8
  start           0   0   0   0   0   0   0   0   0
  +5 on [0,3)     5   0   0  -5   0   0   0   0   0
  -1 on [2,6)     5   0  -1  -5   0   0   1   0   0
  +10 on [4,8)    5   0  -1  -5  10   0   1   0 -10
```

To add 5 over `[0,3)`, we write:

`+5`

at index 0.

Then we write:

`-5`

at index 3.

This means the change starts at 0 and stops at 3.

We do not need to write anything at indices 1 or 2.

For the update `[4,8)`, we write `+10` at index 4 and `-10` at index 8.

Index 8 is one past the last array value.

The extra position allows an update that reaches the end of the array to close correctly.

The difference array does not directly contain the final values.

It contains changes that must later be accumulated.

## Converting differences back to values

<SnippetSource name="23-competitive.prefix-sums" decl="accumulate" />

To get the final values, calculate a running total over the difference array.

Each difference value changes the running total from that point onward.

For example:

```
  idx    0   1   2   3   4   5   6   7
  tot    5   5   4  -1   9   9  10  10
  writing every cell of every range agrees -> true
  6 writes for 3 updates, against 11 cells the slow way
```

The `+5` at index 0 makes the running total 5.

Because there is no change at indices 1 and 2, the running total remains 5.

At index 3, the `-5` removes that update.

The same process applies to all other range changes.

There are three updates.

Each update needs two writes.

So the difference-array version needs six writes.

The direct version touches eleven array cells in total because that is the combined width of the three update ranges.

For larger ranges, the difference becomes much more important.

The final `-10` at index 8 does not appear in the output array because index 8 is outside the original eight values.

Its purpose is to close the update after the last value.

If we continued the running sum through index 8, it would return to zero.

That is a useful consistency check.

## Prefix sums and difference arrays are related

A difference array stores the change between neighbouring values.

For example:

```
  val    3   1   4   1   5   9   2   6
  diff   3  -2   3  -3   4   4  -7   4  -6
  back   3   1   4   1   5   9   2   6
```

The first difference is 3 because the first value changes from an initial 0 to 3.

The next difference is:

`1 - 3 = -2`

The next is:

`4 - 1 = 3`

and so on.

If we take a prefix sum of these differences, we rebuild the original values.

So the two techniques are closely related.

A prefix sum takes values and stores cumulative totals.

A difference array takes values or updates and stores changes between positions.

Their costs are almost opposite.

A prefix array costs O(n) to build and gives O(1) range-sum queries.

A difference array gives O(1) range updates and costs O(n) to convert back into final values.

Choose the technique based on which operation happens many times.

If you have many queries and few updates, prefix sums are a good fit.

If you have many range updates and only need the final array afterwards, a difference array is a good fit.
