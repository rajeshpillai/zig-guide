`make` has a reputation for being a language with strange rules about tabs.
Take away the syntax and two small ideas are left. We build both here, so the
tool is easier to understand.

The first: **the targets form a graph.** `app` needs `main.o` and `util.o`,
each of which needs its `.c` file. Building in the right order means visiting
a node only after everything it depends on, which is a topological sort.

The second: **a timestamp decides whether work happens.** A target is stale if
anything it depends on is newer than it is. This one comparison is why `make`
is faster than a shell script that rebuilds everything.

The stamps stand in for file modification times: higher is newer. `main.c` is

## What just happened

**The build order put the objects before the binary.** Nothing declared that
order. It falls out of visiting dependencies first and appending each target
only on the way back out. This is depth-first post-order, and it is how you
write a topological sort in code.

**Only `main.o` needed rebuilding.** Its source is newer than it is. `util.o`
is newer than its source, so it was skipped. This is where `make` saves time.
On a large project almost everything is up to date, and checking that costs
one integer comparison per target.

**The `state` array is the cycle check.** Each target is
marked 1 while its dependencies are being visited and 2 when it is done.
Meeting a target still on 1 means the graph loops, and the program returns
`error.CircularDependency` instead of recursing until the stack runs out. Real
`make` notices the same thing, prints `Circular b <- a dependency dropped`, and
carries on with the edge removed.

**One thing the program does not model:** once `main.o` is rebuilt, its
timestamp becomes *now*, which makes `app` stale in turn. Real `make`
recomputes as it goes, so staleness moves up the graph. The program above
never runs a command, so it reports a single snapshot of which targets are
stale.

## Check yourself

`make` is famously strict that recipe lines begin with a tab, not spaces.
Given what you have just built, is that rule doing any work?

Almost none, and its author has said as much. The tab distinguishes a recipe
line from a continuation of the rule, which a smarter parser could work out
by itself. The rule stays because changing it would break every Makefile ever
written. Many things in Unix stay the way they are for the same reason. The
graph and the timestamps are the design. The tab is an early choice that could
not be changed later.

## If you have written C

You have almost certainly written a Makefile without writing `make`, and the
translation is direct. A rule's prerequisites are its edges, and `$@` and `$<`
are the target and the first prerequisite of the node you are currently at.

The one thing a C implementation has to do that this program skips is get the
timestamp, with `stat`, and handle the case where the file is not there at
all. A missing target has an mtime of nothing, which has to compare as "older
than everything" so the target gets built. Representing that as 0 is exactly
what the C version does, and it is the correct simplification.
