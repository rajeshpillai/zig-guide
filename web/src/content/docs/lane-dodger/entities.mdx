Blocks and coins are created off the top of the screen and destroyed as they
leave the bottom, several times a second, for as long as the game runs. Two
things follow from that, and the second one is the interesting one.

## No allocator

Storage is a fixed array. A run of any length allocates exactly once, at
startup, and never again. There is no allocator in the simulation at all, which
is also what lets it be a module that imports nothing.

Forty-eight slots is comfortably more than the field can hold. At the tightest
spacing and the highest speed there are about nine rows on screen of at most
three entities each, and the tests assert the peak stays under capacity and
above six, so a change that quietly stops spawning shows up.

## The problem with an index

The obvious way to refer to an entity is its index. It is also the way that
produces a bug you will not reproduce.

An event says "coin 12 was collected". A frame later, slot 12 has been freed and
handed to a newly spawned block. Anything still holding 12 now reads a block and
believes it is a coin. Nothing crashes. The score is occasionally wrong, once an
hour, and never in front of you.

A pointer has the same problem wearing better clothes.

## Generational handles

A handle carries the slot index and the generation that slot was on when the
handle was made. Freeing a slot bumps its generation, so every handle to the old
occupant stops resolving.

<GameSource file="src/sim/pool.zig" decl="Pool" />

The generation is odd while a slot is live and even while it is free, so one
counter answers both "which occupant" and "is anyone home". Generation zero is
never handed out, which gives a null handle for free.

`create` returns an optional rather than asserting. A full pool is not an error
here; the spawner treats it as back pressure and skips the spawn, which is
always safe because the course stays solvable either way.

The first assertion is as important as the second. It proves the slot really was
reused, so the test is exercising the dangerous case rather than passing by
accident.

## One pool, two users

The pool is generic because it is genuinely general. The particle system uses
the same one, with a capacity of 256 and a different element type. Particles are
not part of the simulation; they are the renderer's business. Writing the pool
once meant the renderer got fixed-capacity storage with no allocator without
anybody deciding it should.

## Events

The simulation reports what happened. It does not know what anything will do
about it.

<GameSource file="src/sim/sim.zig" decl="Event" />

Events accumulate in a fixed buffer, drained once per frame by the caller. The
buffer counts what it had to drop, and a test asserts that count is zero across
forty thousand ticks, because a silently truncated event stream shows up as
occasional missing particles and nothing else.

That is where a coin becomes ten amber dots and a small kick of screen shake,
and where the crash becomes debris. The simulation knows about none of it.

## Why the indirection earns its place

This design pays for itself the moment you add something.

Sound was added to this game after it was finished and playing. It required no
change to any rule, because it hooks the same event stream that the particles
already used.

<GameSource file="src/platform/audio.zig" decl="onEvent" />

An event system is easy to over-build. Six variants in a tagged union, a fixed
buffer, and one loop is not an architecture; it is a seam in the one place a
seam was needed. The test is whether adding a reaction requires touching the
thing that caused it. Here it does not, and that is checked by the fact that the
[difficulty tests](/learn/lane-dodger/fair-by-design/) run the entire game with
no renderer, no audio device, and no window.
