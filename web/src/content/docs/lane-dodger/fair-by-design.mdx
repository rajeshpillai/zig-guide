The course generator lays down rows of blocks. They have to get harder and stay
possible.

Getting that wrong does not look like a bug. Every row still leaves a lane open.
The game just becomes unwinnable, and the only report is that people stop
playing.

## There is a floor under the spacing

Between one row arriving and the next, a player may have to cross the whole
board. That costs two lane changes. They also cannot start while the current row
is level with them, because moving sideways into a block beside you is a crash.

The tightest spacing that is still winnable is the sum of those two.

<GameSource file="src/sim/sim.zig" decl="fairnessFloor" />

The second term shrinks as the game speeds up: a faster row spends less time
beside you. The first term never moves.

## Derive the spacing, do not tune it

The first version had two hand-picked constants, an easy spacing and a hard one,
interpolated between. It worked. It was also wrong in a way that surfaces later:
three numbers had to agree, and nothing said so. Change the lane change time and
the hard spacing silently becomes unreachable.

Now the spacing is computed from the floor and decays towards it.

<GameSource file="src/sim/sim.zig" decl="rowGapSeconds" />

The decay never arrives. That fixed the second problem. The earlier curve
reached its hardest setting at sixty seconds and held, so a good player never
lost, and an endless runner nobody can lose has no score worth chasing.

The margin above unwinnable is now one named constant.

<GameSource file="src/sim/config.zig" decl="gap_safety" />

## Prove it by playing it

An argument about four constants is worth as much as the argument is careful. A
program that plays the game is worth more.

<GameSource file="src/sim/bot.zig" decl="targetLane" />

The policy looks at the next two rows, picks a lane open in the first, refuses a
crossing it cannot finish in time, and refuses a path that would slide through a
block currently level with it.

Then a test runs it for four minutes of game time at every seed.

<GameSource file="src/sim/tests.zig" decl="solvable course: the bot survives a long run at every seed" />

It failed the first time it ran. Seed 21, after 8.2 seconds.

## What it found

The bot was steering into blocks it believed it had passed. It discarded
anything whose centre was behind the player's centre, measured with the block's
own half height. The right number is the sum of both half heights. A block whose
centre is 41 units behind you still overlaps you when both bodies are 26 units
tall.

Every unit test passed while this bug existed. The collision code was right, the
generator was right, the spacing was right. The bug was in the reasoning that
joined them, and only a run exercises that.

## Solvable is not the same as playable

A bot with no reaction time surviving a course proves the course is solvable. It
says nothing about whether a person can play it.

So the same policy runs again with a delay in front of it.

<GameSource file="src/sim/tests.zig" decl="Human" />

Pure latency: the decision made from the world as it looked some ticks ago is
the one acted on now. An earlier version counted down a timer and reset it
whenever the ideal lane changed. That livelocked whenever the policy was torn
between two lanes, and made the game look far harder than it is. Measuring the
wrong thing carefully is worse than not measuring.

The numbers it produces are the difficulty curve:

| Reaction | Mean run |
| --- | --- |
| 100 ms | 58 s |
| 150 ms | 46 s |
| 200 ms | 30 s |
| 250 ms | 26 s |
| 300 ms | 24 s |

Half a minute for an unhurried player, a minute for a sharp one, and everybody
loses eventually.

The test asserts the shape, not the values, so the numbers can be tuned without
rewriting it.

<GameSource file="src/sim/tests.zig" decl="a run lasts about as long as a hyper casual run should" />

The last assertion is the one that caught the flat difficulty curve. A sharp
player was averaging the full three hundred second cap, and every other test was
green.

## Two smaller things

**The opening is gentle.** Modelling a 200 ms player gave a mean of 30 seconds
and a worst seed of 3.9. Some openings demanded a two lane crossing before
anyone had settled in. A game that can kill you in four seconds does not get a
second try. Inside a grace window, no row blocks more than one lane.

<GameSource file="src/sim/config.zig" decl="grace_seconds" />

**Coins mark the safe lane.** A coin only ever goes in a lane its own row leaves
open. When a row blocks two of three lanes, the coin sits in the one gap, so
following the coins and playing correctly are the same thing. That is the whole
tutorial for this game, and it is four lines in the spawner.
