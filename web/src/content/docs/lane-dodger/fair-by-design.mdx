The course generator has one job: lay down rows of blocks that get harder and
stay possible. Getting that wrong is the worst kind of bug in a game, because it
does not look like a bug. Every row still leaves a lane open. The game just
becomes unwinnable, and the only report is that people stop playing.

## The floor under the spacing

Between one row arriving and the next, a player may have to cross the whole
board. That costs two lane changes. They also cannot begin while the current row
is level with them, because moving sideways into a block that is beside you is a
crash.

So the tightest spacing that is still winnable is the sum of those two, and it
is not a matter of taste:

<GameSource file="src/sim/sim.zig" decl="fairnessFloor" />

The second term falls as the game speeds up, because a row that is moving faster
spends less time beside you. The first term does not move at all.

## Deriving the spacing instead of tuning it

The first version of this had two hand-picked constants, an easy spacing and a
hard one, and interpolated between them. It worked, and it was wrong in a way
that only shows up later: three numbers had to agree with each other, and
nothing said so. Change the lane change time and the hard spacing silently
becomes unreachable.

So the spacing is computed from the floor and decays towards it.

<GameSource file="src/sim/sim.zig" decl="rowGapSeconds" />

The approach is exponential and never arrives. That is the second thing this
fixed. The earlier curve reached its hardest setting at sixty seconds and then
held, which means a good enough player never loses, and an endless runner nobody
can lose has no score worth chasing.

The margin above unwinnable is now a named constant with a reason attached,
rather than an accident of two endpoints agreeing with a third.

## Proving it, by playing it

An argument about four constants is worth exactly as much as the argument is
careful. The proof is a program that plays the game.

<GameSource file="src/sim/bot.zig" decl="targetLane" />

The policy looks at the next two rows, picks a lane that is open in the first,
refuses a crossing there is not time to finish, and refuses a path that would
slide through a block currently level with it. Then a test runs it for four
minutes of simulated time at every seed.

<GameSource file="src/sim/tests.zig" decl="solvable course: the bot survives a long run at every seed" />

That test failed the first time it ran, at seed 21, after 8.2 seconds.

## What it found

The bot was steering into blocks it believed it had already passed. It filtered
out anything whose centre was behind the player's centre, using the block's own
half height. The right number is the sum of both half heights: a block whose
centre is 41 units behind you is still overlapping you when both bodies are 26
units tall.

<GameSource file="src/sim/bot.zig" decl="reach" />

A test for it now states the case in its title:

This is the argument for testing a game by playing it rather than by checking
its parts. Every unit test passed. The collision code was right, the generator
was right, the spacing was right. The bug was in the reasoning that connected
them, and the only thing that exercises reasoning is a run.

## The test that says whether a person can play it

A bot with no reaction time surviving a course proves the course is solvable. It
says nothing about whether it is playable, and those are different claims.

So the same policy runs again with a delay in front of it.

<GameSource file="src/sim/tests.zig" decl="Human" />

Pure latency: the decision made from the world as it looked some number of ticks
ago is the one acted on now. An earlier version counted down a timer and reset
it whenever the ideal lane changed, which livelocked whenever the policy was
torn between two lanes, and made the game look far harder than it is. Measuring
the wrong thing carefully is worse than not measuring it.

The numbers this produces are the difficulty curve, stated plainly:

| Reaction | Mean run |
| --- | --- |
| 100 ms | 58 s |
| 150 ms | 46 s |
| 200 ms | 30 s |
| 250 ms | 26 s |
| 300 ms | 24 s |

Half a minute for an unhurried player, a minute for a sharp one, and everybody
loses eventually. The test asserts the shape rather than the values, so a
designer can move the numbers and still be told when the game has stopped being
a game.

<GameSource file="src/sim/tests.zig" decl="a run lasts about as long as a hyper casual run should" />

The last assertion in there is the one that caught the flat difficulty curve. A
sharp player was averaging the full three hundred second cap, and every other
test was green.

## Two smaller things the tests pinned

**The opening is gentle.** Modelling a 200 ms player gave a mean of 30 seconds
and a worst seed of 3.9. Some openings happened to demand a two lane crossing
before anyone had settled in, and a game that can kill you in four seconds on
your first go does not get a second one. Inside a grace window, no row blocks
more than one lane.

<GameSource file="src/sim/config.zig" decl="grace_seconds" />

**Coins mark the safe lane.** A coin is only ever placed in a lane its own row
leaves open. When a row blocks two of three lanes, the coin is sitting in the
one gap, so following the coins and playing correctly are the same thing. That
is the entire tutorial for this game, and it is four lines in the spawner.
