A typed query builder in Zig takes columns as `std.meta.FieldEnum(T)`,
so a misspelled column is a compile error, and renders values as
numbered placeholders (`$1`, `$2`) that never touch the SQL text. The
builder is a plain value and chains without an allocator.

## The problem

Every database library faces the same two failure modes. The first is a query
that names a column which does not exist, found at runtime in production as a
database error. The second is a value spliced into the SQL string, found as an
injection. A Zig library can rule out both at the type level, and the code
needed is small.

## The pattern

1. `std.meta.FieldEnum(T)` turns the schema struct's field names into an
   enum. A filter takes that enum, so `.where(.emial, .eq)` is a compile
   error with the misspelling in it.
2. The builder is a plain value. `where` copies it, appends to a bounded
   array, and returns the copy, so the caller can fork a base query
   freely.
3. `render` writes numbered placeholders, and the values travel to the
   driver separately.

## What the enum buys

The `Field` enum exists only at compile time; by runtime a filter is an
integer tag. `{t}` formats the tag name back into SQL, so the enum both
checks the column and supplies its name. That gives three properties: a typo
fails to compile, the check costs nothing at runtime, and there is no string
table to keep in sync with the schema.

The same technique works beyond ORMs. Any library that accepts "one of this
struct's fields" as an argument (sorters, serializers, diff tools) can take
`FieldEnum(T)` instead of a string and move the failure to compile time.

## Why the builder is by-value

`where` returning a modified copy makes the builder immutable in practice: a
shared base query cannot be corrupted by one call site adding its filters. The
bounded array keeps the copy cheap and the API allocator-free, at the cost of
a fixed capacity. State that trade-off in your library's documentation as a
design decision, instead of hiding it as an implementation detail.

## In a full ORM

The real builder grows operators, `ORDER BY`, joins, and an `insert` path, and
pairs each placeholder with a typed value list for the driver. The draft this
section distills from renders to PostgreSQL and SQLite dialects from the same
builder; the dialect switch lives in `render`, in the same place this snippet's
SQL formatting lives.
