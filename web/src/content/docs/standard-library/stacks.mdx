Push and pop in Zig are `append(gpa, x)` and `pop()` on a `std.ArrayList`,
with `pop()` returning `null` when the list is empty. When the maximum depth
is known, a fixed array and a length index make a stack with no allocator at
all.

<Playground name="03-standard-library.stacks" />

Zig has no dedicated `Stack` type because it does not need one. An `ArrayList`
used from the end is a stack:

| Operation | Call |
| --- | --- |
| push | `append(gpa, x)` |
| pop | `pop()` (returns `?T`) |
| peek | `last()` (returns `?T`) |
| size | `items.len` |

Both `pop()` and `last()` return an optional, so the empty case is handled by
the type rather than by a precondition you might forget.

If you learned this from an older tutorial, peek was `getLast()`, and it
returned a `T`. It asserted the list was not empty, so calling it on an empty
list was a safety-checked panic in a debug build and undefined behaviour in a
release one. That call is still there, marked deprecated, and it still
asserts. `last()` is the replacement and returns `?T`, which moves the empty
case into the type. `getLastOrNull()` is a deprecated alias for `last()`.
There is also `lastPtr()`, which returns `?*T` when you want to modify the top
element in place rather than copy it.

Using the end, not the front, is what makes it cheap. Removing from the back
is one decrement of the length. Removing from the front would shift every
remaining element. This is why a stack fits an array well and a queue does
not.

## When the depth is bounded

If you know the maximum, skip the allocator entirely: a fixed array plus a
length index is a complete stack with no failure mode. This matters for
embedded targets and hot paths, and in Zig it is ordinary code.

```zig
var buf: [64]Frame = undefined;
var top: usize = 0;

buf[top] = frame; top += 1;   // push
top -= 1; const f = buf[top]; // pop
```

No allocator means no `try` on push, which changes the shape of the code that
uses it. A parser with a bounded nesting depth has no error path for "ran out
of stack", only a check against the limit. Write that check. With it, deeply
nested input is rejected. Without it, the program crashes.

## Where you will actually want one

Almost every case where you need to remember what to come back to.

- **Matching brackets**, in a parser or a linter. Push on open, pop on close,
  compare.
- **Depth-first traversal** of a tree or a graph, written iteratively so it
  cannot overflow the machine's own stack on deep input.
- **Undo history**, where the most recent action is the first to reverse.
- **An evaluator** for postfix expressions, which is exactly a stack machine.

The [tiny language](/learn/tiny-lang/) track uses the second and fourth of
those. It uses them to trade recursion for an explicit stack.

## Why not a linked list

A linked-list stack allocates per element and scatters them across memory.
`ArrayList` amortises to one allocation and keeps everything contiguous. That
is faster for almost every real workload. Reach for a linked list only
when you need stable addresses or O(1) splicing.

The difference is more than a small constant factor. A pop from an array
reads memory the CPU has already fetched. A pop from a linked list follows a
pointer to memory that is not in the cache, and waits. Textbooks
present the two as equivalent because they compare instruction counts.
Instruction counts stopped deciding performance decades ago.

There is one real exception. If something else holds pointers to the
elements, an array cannot be used, because growing it moves everything. In
that case the extra allocations give you something.
