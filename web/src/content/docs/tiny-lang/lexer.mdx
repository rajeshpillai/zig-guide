A compiler is a short pipeline of programs. Each one takes the output of the
one before and knows almost nothing about the others. This section builds that
pipeline. The first stage turns characters into words.

Source code arrives as bytes. `let total = 0;` is fourteen of them, and
nothing in there says that `let` is a keyword or that `total` is one name
and not five letters. Deciding that is *lexing*. Doing it as a separate pass
makes every later stage easier to write. The parser never sees a space, never
counts a digit, and never checks whether an identifier starts with a
keyword.

## What just happened

**Whitespace is gone.** The parser in the next chapter will never handle a
space, a tab, or a newline. They are consumed here and produce no token, so
every later stage is simpler. The line number stays, attached to each token.
An error message without a line number is nearly useless, and this is the last
stage that still knows the line.

**`total` came out as one token, not five.** The scan is greedy: once a letter
starts a word, it keeps taking letters and digits until it meets something
else. Because of this one rule, `total3` is one identifier. `3total` is a
number followed by an identifier, and the parser will correctly reject it.

**A keyword is an identifier that was found in the keyword table.** The
scanner does not try to match `let` first. It scans the whole word and then
checks the table. Only this order works: matching `let` first would lex
`letter` as `let` followed by `ter`. Every language with keywords does it this way.

**`=` and `==` are why lookahead exists.** After consuming `=`, the scanner
peeks at the next character before deciding which token it made. One character
is enough for this language, and for most languages. When a language needs
more, that has a real design cost. That cost is why `>>` in old C++ template
syntax was a well-known problem.

**Nothing was allocated.** Every token's `text` is a slice pointing back into
the source. Producing them copied nothing, and the tokens become invalid once
the source goes away. [sort](/learn/unix-tools/sort/) made the same borrowing
decision, and a compiler makes it too.

## Check yourself

The lexer never rejects `let let = 3;` or `4 5 6`. Should it?

No. The split is on purpose. A lexer's job is to say what the *words* are.
It does not check whether the sentence makes sense. Both inputs are valid
token streams. Both are also errors, and the parser will report them. With two
separate stages, an error message can say which stage failed.

## If you have written C

The C version of this is a `switch` on the current character inside a loop,
with an enum of token types and a struct holding a pointer, a length and a
line number. The code above does the same. There are a few small
differences.

C's token would hold `char *start; int len;` as two fields you keep in step by
hand. A Zig slice is those two fields, and the language keeps them
together.

And C's keyword lookup is usually a chain of `strcmp` calls. The version here
uses a comptime `inline for` over a table, so the comparisons are generated
but the table is written once. Neither is a hash, and neither needs to be at
seven keywords.
