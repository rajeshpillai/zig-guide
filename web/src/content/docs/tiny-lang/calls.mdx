The compiler and the VM stopped before functions. Calls are not hard to
implement. But implementing them means answering four questions that have no
obvious answers. The set of answers is called a **calling convention**.

1. Where do the arguments go?
2. How does the callee find its own variables?
3. Where does the machine go when the function returns?
4. Who removes the arguments afterwards?

Each question has more than one answer, and real machines choose differently.
Code built with one convention cannot call code built with another. That is
why you cannot link a library built with different conventions.

## The answers this one gives

**Arguments go on the stack, pushed by the caller, in order.** That is the
oldest answer and the simplest. Real machines put the first few in registers
because that is faster. For example, "the System V AMD64 ABI passes the first
six integer arguments in `rdi, rsi, rdx, rcx, r8, r9`".

**A local is a slot counted from the frame base.** When a call begins, the base
points at the first argument the caller pushed. So parameter 0 is at base + 0.
The callee never has to be told where its arguments are, because they are
already on the stack at its base. Nothing is copied.

**The return address is saved by the call.** The instruction pointer already
points past the `call` when the frame is pushed, so saving it costs no extra
work.

**The callee cleans up.** On `ret` it resets the stack to the frame base, which
discards the arguments, and then pushes the result. The other choice is for
the caller to clean up, which is what C does. C does it because of variadic
functions: `printf` cannot clean up arguments when it was never told how many
there are.

## What just happened

**`square`'s body is four instructions.** `load_local 0` twice, `mul`, `ret`.
The `push 0` after them in the listing is the epilogue every function gets,
for the case where control reaches the end without a `return`.
The body has no name lookup and copies no arguments. The parameter `n` became
slot 0 at compile time. Reading it at run time is one array index from the
frame base.

**`fact(5)` recursed through compiled bytecode and gave 120.** Each call pushed
a frame; each `ret` popped one. The recursion works because the frame base is
per-call. Five frames existed at once, at different stack offsets. The frames
chapter showed the same thing in the tree-walking interpreter.

**A jump goes around each function body.** Bodies are emitted inline, in the
middle of the program, so running straight through would fall into `square`
without anybody calling it. The jump is patched once the body's length is
known. This is the same backpatching the compiler chapter used for `if`.

**The function is registered before its body is compiled.** This order makes
recursion possible: when the compiler reaches `fact(n -
1)` inside `fact`, it needs to already know that `fact` exists.

## Check yourself

The compiler resolves a name to a local slot only if it is a parameter of the
enclosing function. What happens to `let x = 1;` written inside a function
body?

It becomes a **global**, shared by every call. That is wrong, and it is one of
the limitations this compiler still has. The same silent `else` prong drops
`while` loops and compiles `/` as an equality test. Real locals need a scope
resolver that walks the body first, collects every declaration, and assigns each one a slot
above the parameters. The frame is then sized to hold both, and the base
pointer addresses all of it uniformly.

With that resolver, a function has its own scope, not just arguments. It is
the next thing to build if you take this further. Without it, the tree-walking
interpreter and this compiler still accept different programs. A language with
two back ends often has gaps like this.

## If you have written C

You have seen this convention's output every time you read a disassembly. The
prologue and epilogue GCC emits are exactly the bookkeeping above:

```
push rbp          ; save the caller's frame pointer
mov  rbp, rsp     ; this frame's base
sub  rsp, 32      ; room for locals
...
leave             ; undo it
ret               ; jump back
```

`rbp` is the frame base. A local at `[rbp-8]` is the slot arithmetic above,
with a real register doing the work. A debugger can print a stack trace
because each frame stores the previous frame pointer. Walking that chain
recovers the call history. It is the frame array from this chapter, stored as
a linked list in memory.

The convention is also why a stack overflow in C is a segfault, not an error.
Nothing checks the depth, because checking would cost an instruction on every
call. This VM checks. It can afford to, because it already pays for a switch
dispatch.
