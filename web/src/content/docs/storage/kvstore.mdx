The last chapter ended on a problem it could not solve: two files that have to
agree, and a crash between writing one and the other. This problem is not
specific to files. It happens with any change that is not a single indivisible
act.

The answer is old and simple. It is used by every database, every journalling
filesystem and most message queues. **Write down what you are about to do,
then do it.** If the power goes out before you finish, the note is still there
when the program restarts, and you do the change again.

That note is a **write-ahead log**. Recovery is reading it.

## What just happened

**A clean shutdown replayed all four records.** The in-memory store was rebuilt
from the log alone. The log is the database. The in-memory store is a fast
cache of it.

**The crash lost the record that was mid-write, and nothing else.** Truncating
the log to simulate a power failure left a final line with no newline. Replay
stopped there, and the first three records were fine. `c` is absent, which is
correct: that write never completed, so it never happened.

A WAL works because of this property. A partially written record at the
**end** of an append-only file is detectable when the process dies, because a
record is complete only once its terminator has been written. Nothing before
it can be affected, because nothing before it was touched.

**The corrupted byte was caught by the checksum, and replay stopped.** The
newline framing cannot see this. The record has its terminator, but its
content is wrong. Only the checksum notices.

Stopping had a cost. Records three and four were readable and were refused
anyway. This is deliberate. A log is a **sequence**, and a
record after a damaged one may depend on the one that was lost. Applying the
readable remainder gives you a store that never existed at any point in time.
A store missing its last records is the better outcome. The store built from
the readable remainder looks correct, and you cannot tell by looking that it
is wrong.

## What this program cannot show you

`fsync`. Writing to a file puts the bytes in the operating system's page
cache. The kernel writes them to the disk later, at a time it chooses. If the
power fails in between, the write is gone, and on recovery the log will show
that it never happened.

`fsync` is the call that says "write this to the disk now, and do not return
until you have". A WAL without it protects you when your process dies, but not
when the machine dies. `fsync` is also slow. That is why databases have a
durability setting, and why the fast setting is fast.

This page cannot demonstrate `fsync`, because there is no disk here. The
mechanism above is complete, but the durability guarantee is not.

## Check yourself

The log grows forever. Every `set` appends, even to a key written a thousand
times. What stops a real system from filling the disk?

A **checkpoint**. Recovery then means loading the last checkpoint and
replaying only what came after it. That also makes startup fast: without
checkpoints, a database that has been running for a year replays a year of
history every time it starts.

This is the same idea as the tombstones from the first chapter, at a larger
scale. An append-only structure needs a periodic process to reclaim
what is dead, and in an LSM tree that process is called compaction.

## If you have written C

`write` then `fsync`. The two hazards are ordering and false success.

Ordering: the log write must reach the disk **before** the change it
describes. It must come before, not at the same time. If the database file is updated first
and the machine dies, the log has no record of a change that has already
happened, and recovery cannot undo it. That is why it is called write-*ahead*.
If you get the order backwards, the system passes every test and loses data
the first time the machine dies at the wrong moment.

False success: `fsync` has historically returned success without the data being
durable on several combinations of filesystem, controller and drive with write
caching enabled. PostgreSQL has a well-known write-up of discovering that
error handling on a failed `fsync` also differed by kernel version, in ways
that could lose data silently. So `fsync` alone does
not make data durable. The filesystem, the controller and the drive all have
to keep their promise too.
