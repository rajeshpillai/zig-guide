An HTTP request is text, and small enough to read out loud:

```
POST /submit?id=7 HTTP/1.1
Host: example.com
Content-Length: 13

name=ada&ok=1
```

A request line, some headers, a blank line, and a body. That is the whole
format, and you can implement it without a library.

The awkward part is the blank line. Its job looks simple, but it is not. HTTP sends **no length up front**. A server
reading from a socket has no idea how many bytes belong to this request, so it
cannot ask for them. It has to read until it sees the header section end, and
only then can `Content-Length` tell it how much body follows.

That is the framing problem from the [networking](/learn/networking/framing/)
section, and HTTP's answer is a delimiter: `\r\n\r\n`.

## What just happened

**The parse is a split, then a split, then a loop.** Find the blank line to
separate head from body, split the head on `\r\n`, take the first line as the
request line, and treat the rest as `name: value`. The parser needs no state
machine and no buffering, because the whole request is already in memory.

**`Content-Type` was found when it was sent as `content-type`.** Header names
are case-insensitive, and the parser has to handle that from the start. `curl`
sends `Host`, HTTP/2 clients lower-case everything, and a hand-written client
sends whatever its author typed. A parser that compares names exactly works
with the client you tested with, and fails with the others.

**Whitespace is trimmed after the colon and not before it.** `Host: example.com`
and `Host:example.com` are both fine. `Host : example.com` is malformed.
Accepting it anyway sounds harmless, but it is not. When two systems in a chain
disagree about which requests are valid, an attacker can make one of them see
a request the other did not. That is how request smuggling works. Strict
parsing protects against it.

**Nothing was copied.** Every field is a slice of the original bytes. The
request is a view over the buffer the socket filled, so parsing allocates
nothing and the whole thing is valid exactly as long as that buffer is.

**Four malformed requests were rejected.** A request line with no version, too
many parts in the request line, a header with no colon, and a request that
stops before the blank line. The parser returns an error for each one and does
not guess.

## Check yourself

The parser takes `[]const u8` and never mentions a socket. Why does that
matter?

Because it means this page can run it. The same property is what lets the
parser be unit-tested without a network, fuzzed with a corpus of malformed
requests, and reused by a client, because a
*response* has the same shape: a status line, headers, a blank line, a body.
The status line needs its own split, since this parser wants exactly three
fields and a reason phrase like `Not Found` has a space in it. A parser that
reads from a socket can be tested only by starting a server.

Every protocol parser in this guide is written this way. That is why most of
the networking chapters run in a browser. The next chapter puts a socket in front
of this one, and the parser does not change.

## If you have written C

The C version uses `strstr` for the blank line and `strtok` for the rest. Both
choices have a cost.

`strtok` writes `\0` over each delimiter, destroying the buffer as it reads.
For a request that is often acceptable, since you are done with it. It also
collapses runs of delimiters, which means an empty header line, the very thing
marking the end of the headers, disappears. Parsers built on `strtok` usually
find the blank line separately for this reason.

And every field ends up as a `char *` into the buffer with no length, so
"header value" and "the rest of the request from here on" are the same type.
This same type is what lets a bug read a request body as a header value.
