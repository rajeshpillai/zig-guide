[The scene graph](/learn/graphics/scene/) stored two integers per node, and
noted the limit: two integers only let a node move. A full scene graph stores
a matrix, so a node can turn and resize as well. Composing a parent with a
child then becomes a multiply. This chapter builds that matrix.

## What just happened

**Six numbers cover every case.** Moving, turning, scaling and shearing are
four ways of filling in the same six slots. A routine that applies a transform
does not know which of them it was handed.

**Order changes the answer.** The two arrows in the first picture come from the
same quarter turn and the same offset, composed both ways round. Rotation is
about the origin, so moving first means turning the offset too, and the shape
travels a quarter circle to a different place. The picture shows that matrix
multiplication is not commutative.

**Turning about a point is three transforms.** There is no `rotate` that takes
a centre. Move the pivot to the origin, turn, and move it back. Those three
compose into a single matrix, and applying it costs the same as one rotation.
The arrows numbered 1, 2 and 3 move around the `+`, but no code for an orbit
exists. Each one is just this matrix with a different angle.

**The shape is never modified.** `shape` is one array of seven points, `const`,
drawn eight times across the three pictures. Every difference is in the
matrix.

## Reading a composition

In practice, transforms are awkward because the usual way to write them runs
backwards from the order things happen. As matrices, applying
`A` and then `B` to a column vector is `B * A * p`: the one nearest the point
acts first, so the chain reads right to left.

`then` exists to hide that. `a.then(b)` means `a` first, and internally it
computes `b * a`. The reversal happens once, in one function. Nobody reading
the call has to reverse it in their head:

```zig
const about_pivot = Transform.translate(-pivot_x, -pivot_y)
    .then(Transform.rotate(quarter_turn * steps))
    .then(Transform.translate(pivot_x, pivot_y));
```

The code lists three operations in the order they occur. It builds the same
matrix a graphics textbook would write as `T * R * T⁻¹`.

The display's aspect ratio is composed the same way. A character cell is about
twice as tall as it is wide, so every point gets a final non-uniform scale of
`(2, 1)`. This scale is kept out of the transforms above, so a rotation in
this program keeps the shape's angles correct. The shape is worked out in
square units and squashed once, at the end, by a matrix like any other.

## What the bottom row is for

The matrix is 3x3 but only six numbers are stored. The missing row is always
`0 0 1`, so there is no need to store it.

The row exists because translation is not a linear operation. A 2x2 matrix multiply
can rotate, scale and shear, and every one of those leaves the origin where it
is. Nothing built from `a`, `b`, `c` and `d` alone can move a point away from
the origin. Adding a third coordinate fixed at 1 gives translation a column to
live in. The last column is that column: its entries are multiplied by the 1
and added, which is exactly what a move does.

This extra coordinate is what homogeneous coordinates means. With it,
translation becomes a multiply like the others. So a chain of moves, turns and
scales collapses into one matrix. Each point is multiplied by that one matrix,
instead of going through every step of the chain.

Perspective goes one step further. Let the bottom row hold something other
than 0 and 1, and divide by the third coordinate afterwards. The division is
what makes the far end of a wall smaller. The trapezoid in [texture
mapping](/learn/graphics/texture/) was missing this division.

## Check yourself

`then` builds a new matrix by multiplying. Why not skip it and apply each
transform to the points in turn?

For seven points it makes no difference. The reason is what happens when there
are seven thousand, or when the chain is deep: composing costs one multiply
per *transform*, applying costs one per *point*. Fold the chain first and
every point pays for one matrix, regardless of how many operations went into
it. For the same reason, the scene graph adds up an offset on the way down the
tree, instead of walking again from the root at every node.

The second reason is accuracy. Each application rounds, so applying five
transforms in turn rounds five times per point. Composing rounds once while
building the matrix, and the points are transformed once.

## If you have written C

The struct is the six-float affine matrix from every 2D graphics API you have
met. Cairo's, Direct2D's, the six arguments to the web canvas `setTransform`,
and Java's `AffineTransform`. Field order and naming differ, but the six
numbers are the same.

The Zig version has two differences. The trigonometry uses builtins instead of
libc calls, so this snippet has no dependency to link and runs unchanged in a
browser, which is how the program above runs in this page.

The default field values in the struct declaration also matter.
`identity` is `.{}`, and each constructor sets only the fields it needs:
`translate` writes `e` and `f`, and the other four keep the identity's
`1, 0, 0, 1`. In C those are four more assignments per constructor. Forgetting
one gives a common bug: a translate that silently sets the scale to zero.
