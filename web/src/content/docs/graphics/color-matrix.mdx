Grayscale, sepia, saturation, hue rotation and channel swaps look like
separate filters. They are one filter with different constants: a 3x3 matrix
multiplying the channel vector.

```
[ R' ]   [ a b c ] [ R ]
[ G' ] = [ d e f ] [ G ]
[ B' ]   [ g h i ] [ B ]
```

Writing them this way lets them multiply. A chain of four colour filters
becomes one matrix, computed before the image is touched, and then one pass
over the image.

## Grayscale, written as a matrix

Put the luma weights in all three rows:

```zig
const luma_matrix: Matrix = .{
    77, 150, 29,
    77, 150, 29,
    77, 150, 29,
};
```

Every output channel becomes the same weighted average, which is grayscale.
The entries are scaled by 256 and the multiply divides by 256 at the end, so
this stays in integers throughout. Floats would add precision that the final
cast to `u8` throws away, and would need a conversion at each end.

## Saturation is a line through grey

```
out = luma + s * (in - luma)
```

At `s = 0` that is grayscale, at `s = 1` the original, and above 1 it keeps
going in the same direction, away from grey. As a matrix it is a blend of the
luma matrix and the identity:

```zig
fn saturation(s: i32) Matrix {
    var m: Matrix = undefined;
    for (&m, identity, luma_matrix) |*out, i, l| {
        out.* = @divTrunc(s * i + (scale - s) * l, scale);
    }
    return m;
}
```

Because it is a matrix and not a special case, it composes with the others.

The output shows that saturation moves chroma and leaves brightness alone:

```
luma under saturation (original, sat 0, sat 200%)
     red disc:  97  97  76
   green disc: 151 151 152
 yellow block: 212 212 209
```

Grayscale preserves luma exactly, because the grey it produces is defined as
the luma. At 200% the numbers drift, and the red disc drops from 97 to 76.
The cause is clipping. The maths is correct. Pushing red past 100% saturation
pushes the channels past 0 or 255, where they are clamped. A clipped colour no
longer has the luma the matrix asked for. So any saturation control, pushed
far enough, loses brightness in the colours it was supposed to intensify.

## Sepia's rows do not sum to 256

```zig
const sepia: Matrix = .{
    101, 197, 48,
    89,  176, 43,
    70,  137, 34,
};
```

Those rows sum to 346, 308 and 241. A row summing to 256 preserves brightness.
These rows do not, on purpose. Sepia is meant to brighten the image as it
tints it, and the red row gains the most, which gives the warm colour. If you
"correct" the rows to sum to 256, you get a muddy grey-brown that looks
nothing like sepia.

So know which kind of matrix you have. A matrix that sums to more than 256 by
mistake blows out highlights for no reason.

## Composition, and what it costs

The product of two colour matrices is the matrix that applies both:

```zig
fn compose(a: Matrix, b: Matrix) Matrix { ... }  // applies b first
```

Sepia after 62% saturation, as one matrix:

```
  +100 +198  +43
   +89 +177  +38
   +70 +138  +30
```

One pass over the image instead of two, and the saving grows with the length
of the chain. A photo app applying six adjustments does one matrix multiply
per pixel instead of six.

The composition is not exact:

```
two passes vs one composed matrix: 1560 of 2048 pixels differ, by at most 1
```

Two passes round to a byte in between. The composed matrix rounds once, inside
the matrix product. The lookup tables in
[per-pixel transforms](/learn/graphics/per-pixel/) were different: composing
them was exact to the last bit. A table maps bytes to bytes, so composing adds
no error. A matrix carries fractions, and rounding them earlier or later gives
different answers.

Off by one per channel is too small for anyone to see, and the two-pass
version is the more accurate of the two. Composing truncates the nine matrix
entries themselves, and each of those errors is then multiplied by a channel
value as large as 255. Rounding twice on the way through loses less than
rounding the matrix once. This affects testing: the same filter with a
different order of operations does not give bit-identical output, and a test
that compares images byte for byte will fail on it.

## What a matrix cannot do

**Anything spatial.** A colour matrix reads one pixel. Blur, sharpen and edge
detection need neighbours, which is
[convolution](/learn/graphics/convolution/), a different loop with a different
cost.

**Anything non-linear.** Gamma, curves and thresholds are not linear functions of
the channels, so no matrix expresses them. Those are lookup tables. A full
pipeline mixes both: tables for the curves, a matrix for the colour mixing.

**Alpha.** These are 3x3 over RGB. Systems that include alpha use a 4x5 (four
rows, four coefficients plus a constant offset), which is what the CSS
`feColorMatrix` filter and Android's `ColorMatrix` both take. The extra column
is what lets a matrix add a constant, and that is how tinting toward a fixed
colour works.

Everything on this page also multiplies sRGB bytes directly. The warning from
[alpha blending](/learn/graphics/blending/) applies here too: those bytes are
not linear light. Colour operations that need to be accurate convert to
linear first.
